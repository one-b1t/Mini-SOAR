## 1. Yang SUDAH Selesai

### 1.1 Perimeter dinonaktifkan (28/09)

Cloudflare, FortiGate, dan Kaspersky dimatikan **total** karena tidak dimiliki di
tempat kerja. Kontrolnya satu konstanta:

```python
# minisoar/config.py
PERIMETER_NONAKTIF = frozenset({"cloudflare", "fortigate", "kaspersky"})
```

File connector **sengaja tidak dihapus** supaya mudah dihidupkan kembali.

Guard dipasang di 5 jalur, bukan hanya di orchestrator, karena celah bypass
terbukti ada di semua lapisan:

| Lokasi | Yang dijaga |
|---|---|
| `config.py:get_configured_providers()` | memaksa `False` meski env terisi |
| `mitigation/core.py` | `trigger_auto_block/unblock` menolak sebelum dispatch |
| `playbook/actions.py` | `mitigation.cloudflare_block` / `fortigate_block` |
| `bot.py` | 7 handler menolak eksplisit |
| `mitigation/cloudflare.py`, `fortigate.py` | guard **di dalam connector** |

Poin terakhir penting: `from minisoar.mitigation.cloudflare import block_ip`
mengبيعات seluruh atribut paket, jadi guard di `__init__.py` tidak akan
menolong. Guard harus di dalam file connector itu sendiri.

### 1.2 Enam kelas bypass ditutup

1. Orchestrator — sudah ada sebelumnya
2. Playbook — `actions.py` mengimpor `block_ip` langsung
3. Re-export paket — `mitigation/__init__.py` mengekspor modul
4. **Direct connector** — `block_ip()` dipanggil tanpa lewat orchestrator
5. Harness E2E — `HANDLER_PERIMETER` memetakan via substring
6. **Celah `/trace_imperva`** — handler bernama `tracev`, tidak mengandung
   kata "imperva", jadi lolos dari exclusion. Diperbaiki dengan mengganti
   mekanisme: `CASES` kini 5-tuple dengan kolom perimeter eksplisit, dan
   `HANDLER_PERIMETER` dihapus total

Harness E2E sekarang: 38 kasus total, **22 yang boleh jalan di mode real**.

## 5. Model ML — TEMUAN TERPENTING

### 5.1 Tidak ada model sungguhan di mesin ini

`baseline_model.joblib` (827.493 B) dimuat langsung dan diperiksa:

```
metrics : accuracy 0.8404, roc_auc 0.8796, total_samples 10000
trained : 2026-09-28T10:37:51 UTC
columns : identik dengan minisoar/ml/export.py:55-63
```

Generator itu `random.Random(42)`, 10.000 baris, komentarnya sendiri menulis
*"ML bootstrap simulation"*. **AUC 0,88 di metadata adalah angka dari data palsu.**

`active_model.joblib` (2.251 B) yang dimuat duluan di `inference.py:25`:
9 fitur, LogisticRegression, **`decision_threshold = 0.1`**, accuracy 1.0 pada
200 sampel — overfit.

Dinilai pada data produksi lewat `predict_block` asli:

| Model | AUC | Perilaku |
|---|---|---|
| `baseline_model.joblib` | **0,267** | lebih buruk dari acak |
| `active_model.joblib` | 0,870 | konservatif, jarang memblokir |

Baseline pada ambang mana pun hanya bisa "blokir semua" atau "blokir nol".

### 5.2 Akar masalahnya: satu baris query

`minisoar/ml/export.py` menjalankan query join dengan `{"terms": {"event_id": chunk}}`.
Field `event_id` bertipe **`text`, bukan `keyword`**. Query `terms` pada field
`text` tidak pernah menghasilkan hit. Rantainya:

```
extract_minisoar_samples() → []
        ↓
write_synthetic_dataset()   ← random.Random(42)
        ↓
baseline_model.joblib
```

**Sudah diperbaiki di `64e8de6`.** Sekarang memakai
`bool.should: [event_id.keyword, rule.id.keyword]` plus fallback skema ECS
(`rule.name`, `observer.vendor`, `event.severity`).

Bukti produksi: **sebelum 0 baris → sesudah 2.071 dari 2.071 label.**
TDD diverifikasi lead: kembalikan ke kode lama → 4 test gagal; di kode baru → hijau.

Jalur fallback ke data sintetik sekarang memberi **warning**, tidak diam lagi.

### 5.3 Kenapa model tetap tidak dipromosikan

Data produksi berhasil ditarik, tapi tidak layak dilatih. Kandidat terbaik
(RandomForest 5 sinyal, AUC 0,959, stabil antar seed) **ditolak**, alasannya:

**a. Seluruh daya diskriminasi berasal dari satu `detector_type`.**

| detector_type | % berlabel block |
|---|---|
| `alert_gambling_slot` | 63,3 |
| `alert_url_minor` | 97,7 |
| `alert_webshell_immediate` | 97,5 |
| `alert_random_url` | 100 |
| `alert_url_major` | 100 |

Dari 33 label negatif, **29 adalah `alert_gambling_slot`**. Model sebenarnya
belajar satu aturan: *gambling_slot biasa saja, yang lain ancaman*.

**b. Detector yang tak pernah dilihat akan diblokir.** Probe dengan
`alert_generic`: kandidat **memblokir 100%**. Padahal daemon memancarkan
`sqli_attack`, `xss_attack`, `lfi_attempt`, `rce_heur`, `generic`,
`distributed_error`, `dst.` — data latih cuma punya 5. Pada 5.000 event
terbaru ada `alert_distributed_error` yang **nol** di data latih.

**c. Minority class terlalu kecil dan basi.** 33 `ignore`, semuanya
Jan–Februari 2026. `recall_ignore` di holdout diukur dari 8 sampel,
CI 0,68–1,00.

**d. 84% sampel adalah label sistem sendiri.** `semi_auto_block` 1.732 baris
(semua label 1) — **feedback loop**, sistem dilatih pada keputusannya sendiri.
Label manusia hanya 339.

**e. `reputation_score` dan `is_whitelisted` konstan 0** di seluruh 2.071 baris.
Reputasi AbuseIPDB adalah sinyal TI terkuat di runtime (`daemon.py:507`),
tapi tidak pernah tersimpan ke event yang dibaca.

**f. SecureSphere menenggelamkan 83% data.** `ES_SECURESPHERE_ENABLED=true`,
`MAX=10000`. 10.000 dari 12.071 baris, 100% Imperva, dengan detector yang tidak
pernah diproduksi daemon. Itulah asal `dataset.csv` lokal (`event_id` berawalan `sec_`).

karena teks sudah `.lower()`; "block" adalah substring dari "unblock".

## 7. Keputusan yang MENUNGGU —.blocker produksi

**Tiga hal di sini tidak boleh diputuskan tanpa pemilik proyek.**

### 7.1 `.env` baris 49: `MINISOAR_MOCK=1` ← **PALING MENDESAK**

```ini
.env:49  MINISOAR_MOCK=1
```

Selama aktif:
- `es_request()` mengembalikan kosong **tanpa menghubungi Elasticsearch**
- `export_dataset_from_es()` langsung skip
- Bot berjalan dalam mode simulasi

**Belum diubah** karena itu keputusan operasional, bukan teknis. Perlu
dipastikan: ini sisa testing, atau memang sengaja? Selama belum diputuskan,
**tidak ada integrasi produksi yang bisa diverifikasi.**

### 7.2 `active_model.joblib` `threshold = 0.1`

Skor model ini menggerakkan **auto-block**. Amanggalat 0,1 dengan model yang
overfit berarti hampir semua event lolos sebagai ancaman.

Opsi: biarkan / turunkan ke baseline (baseline AUC 0,267, juga buruk) /
nonaktifkan auto-block berbasis ML sementara / ganti dengan model baru *(belum
layak, lihat §5.3)*.

### 7.3 Filter `reason_code` untuk training

Sebelum autotrain berikutnya, harus diputuskan:
- filter `reason_code` mana yang boleh dilatih (saran: hanya `telegram_button` dan `ignore`)
- status `ES_SECURESPHERE_ENABLED`
- status `MINISOAR_MOCK` di `.env`

### 7.4 `scripts/cleanup_minisoar_edr_iocs.py` — tanpa rem

Menghapus IoC TrendMicro **massal** berdasarkan pola `description` dan ambang
skor, lewat endpoint tanpa smoke test, berdasarkan **nilai**. Objek TrendMicro
tidak punya `object-ID`. Kalau dijalankan pada data seperti sekarang, akan ikut
menghapus 11 IoC exfiltrasi yang asli. **Belum dirombak.**
